# Verifying the running app

The unit suite (`pnpm run test`) covers pure logic and proves nothing about
whether the app _runs_. A typo in `mustGet('task-list')`, a listener wired to the
wrong element, or a CSS selector that stopped matching all pass lint, typecheck,
tests and the bundle — and ship a blank window. The end-to-end suite is what
catches those.

## Run it

```bash
pnpm run e2e          # the whole suite, headless
pnpm run e2e -- capture   # just the screenshot captures
pnpm run e2e:ui       # interactive, for debugging a failure
pnpm run e2e:report   # open the HTML report after a failure
```

Then **look at the result**: `docs/screenshots/*.png` are regenerated by the
capture tests. Read them. Several real defects in this repo were found by
looking at a screenshot rather than by an assertion.

### If Chromium can't be downloaded

Sandboxes and CI images often ship a Chromium but block Playwright's download.
Point at the existing binary:

```bash
PLAYWRIGHT_CHROMIUM_PATH=/opt/pw-browsers/chromium-*/chrome-linux/chrome pnpm run e2e
```

The config reads that env var and otherwise uses Playwright's managed browser.
Do **not** run Playwright's browser installer (`pnpm exec playwright install`,
or `npx playwright install`) in a sandbox — it will fail on the
network and waste several minutes.

## Why a browser can test a desktop app

`src/lib/tauri.ts` guards every native call behind `isTauri()`, and the vault
falls back to `localStorage`. So the browser runs the _same_ controller,
scheduler and Markdown serializer as the desktop build. Everything above the
native shell is genuinely covered.

**What this does not cover**, and cannot: the tray icon and menu, window
positioning, transparency, always-on-top, launch-at-login, and — most
importantly — whether the window can take keyboard focus under Windows'
foreground-activation rules. Those need a real Windows machine. Never report
them as verified on the strength of a green e2e run. See "Known unknowns" in
`docs/future-work.md`.

## Writing a new case

`e2e/harness.ts` does the setup. `startApp(page, options)` freezes the clock and
seeds the vault through the same `localStorage` keys the browser build uses, so
**no test-only hooks exist in the app itself** — keep it that way.

```ts
await startApp(page, {
  now: new Date(2026, 7, 3, 14, 20), // frozen wall clock
  settings: { workStart: '08:00' }, // merged over 09:00–17:00 weekday
  files: { '2026-08-03.md': dayFile(/* … */) }, // pre-existing vault state
});
```

Two things that will bite you:

- **The clock does not advance on its own.** Use `advanceMinutes(page, n)` to let
  the scheduler tick; it re-evaluates once a minute, so anything shorter can
  never surface a new check-in.
- **A fresh vault always yields a day-start**, whatever hour you set, because the
  first check-in of a day is always the opener. To exercise the hourly card, seed
  a day file with `lastCheckIn`. Asserting the headline you expect is worth it —
  a capture once silently showed the wrong prompt.

## Checklist for "does this change work?"

1. `pnpm run check` — format, lint, typecheck, unit tests.
2. `pnpm run build` — it bundles.
3. `pnpm run e2e` — it runs.
4. Look at `docs/screenshots/`.
5. In `src-tauri`: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
   `cargo check`, `cargo test`.
